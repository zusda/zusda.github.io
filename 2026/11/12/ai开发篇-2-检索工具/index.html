1. Agent 的检索能力

当 Agent 现有的知识不足以回答用户当前的 Query 时，就需要能够主动检索所需的信息。

常见的检索方式主要有三种：

  1. 网络搜索：通过搜索引擎获取互联网上的信息。
  2. RAG 语义检索：从已有的本地资料库中检索相关内容。
  3. 关键词检索：通过 grep 等工具，根据关键词精确查找内容。

本文主要实现前两种方式，并将其封装成 Agent 可以调用的工具。第三种方式相对简单，可以根据实际需求自行实现。

2. RAG

之前的文章介绍过，RAG 本质上可以理解为一个语义搜索引擎。与传统搜索引擎主要依靠关键词匹配不同，RAG 通过 Embedding 模型将文本转换为向量，再根据向量之间的相似度检索相关内容。

具体原理可以参考之前的文章：从零开始的 LLM 6. RAG（检索增强生成）(一)。

这次我们将重新整理 RAG 的实现流程，并将其封装成 Agent 工具。

整个流程可以分为以下几个步骤：

  1. 收集并清洗数据。
  2. 对文本进行切块。
  3. 选择 Embedding 模型。
  4. 选择向量数据库。
  5. 将数据、Embedding 模型和向量数据库组合成 RAG。

以上步骤完成后，就得到了一套可以进行语义检索的 RAG 系统。

在 Agent 工具中，我们统一使用 RAG_search(collection, query, top_k=5) 进行检索。

其中，collection 用于指定检索的数据集合。我们会在工具描述中说明有哪些 Collection 可供选择，以及每个 Collection 包含什么资料、适合检索什么内容。

这相当于一级路由。也可以将 Collection 的选择规则写入 Skill，再通过 Skill 调用其他 Skill，实现多级路由。

2.1 收集、清洗数据

首先，需要将不同来源、不同格式的资料统一整理成标准的数据结构。

例如 PDF、Markdown、Word 等文件，都可以通过相应的解析工具转换成统一格式。

本文使用的资料来自一批导出的 TXT 文件，因此直接读取文件内容并进行统一整理即可。

数据收集方式可以根据实际情况选择，但最终需要统一输出为以下格式：

每个文档对应一条 JSON 数据，包含两个主要字段：

  • metadata：保存文档的属性信息，例如标题、日期、文件路径等，供后续过滤、展示来源和管理文档使用。
  • content：保存文档正文，后续将对其进行切块和向量化。

最后，将整理好的数据保存为本地文件 documents.jsonl。

这里需要明确两者的分工：

  1. metadata 不参与向量计算，主要用于过滤检索结果、展示来源、增量更新和调试定位。其中可以保存带后缀的相对路径，作为文档的唯一标识。
  2. content 是实际送入 Embedding 模型的文本。希望通过语义或关键词检索命中的信息，都应该放在这里。例如在正文开头拼接文件标题，可以让文件名也参与检索。

简单来说：用于检索的信息放进 content，用于管理和展示的信息放进 metadata。

2.2 文本切块

完成数据清洗后，不能直接将整篇文章转换成一个向量。

这是因为一篇文章通常包含多个主题，将整篇文章压缩成一个向量，会使不同主题的信息混合在一起，降低检索的准确性。

因此，需要先将文档切分成多个较小的文本块（Chunk），再分别进行向量化。

切块时需要注意两个问题：

  1. Chunk 大小：需要控制每个文本块的长度，避免单个块包含过多无关信息。
  2. 切分位置：尽量按照句子或段落边界进行切分，避免将完整句子从中间拆开。

这里使用 LangChain 提供的 RecursiveCharacterTextSplitter，并通过自定义分隔符控制切分优先级。

RecursiveCharacterTextSplitter 的内部实现原理可以参考之前的 RAG 文章，这里只做简单说明。

其主要流程如下：

  1. 切分文本：按照分隔符列表的优先级进行切分。例如优先使用 \n\n，其次使用 \n、。 等。如果某个片段仍然超过 chunk_size，则继续使用下一个分隔符切分；如果所有分隔符都无法满足要求，最后才会按照字符长度进行硬切分。
  2. 合并片段：按照原有顺序，将相邻片段合并成 Chunk。当继续添加下一个片段会超过 chunk_size 时，就输出当前 Chunk。
  3. 保留重叠内容：生成下一个 Chunk 时，根据 chunk_overlap 保留前一个 Chunk 末尾的一部分内容，减少切分位置对上下文的影响。

从这里开始，数据处理就进入了标准化流程。只要前面的数据源已经整理成统一格式，后续步骤就可以复用。

在正式切分之前，还需要给每个原始文档分配一个 ID。因为一个文档可能被切分成多个 Chunk，我们需要通过这个 ID 将检索结果重新映射到原始文档。

具体做法是：给每个文档分配一个 ID，并将其添加到 metadata 中。同时构建 dict_id2document，保存 ID 与原始文档之间的映射关系。最终将映射关系保存为本地文件 dict_id2document.json。后续会将该文件部署到 MCP 服务器中，用于根据 Chunk 中的父文档 ID 找回原始文档。

这里有两个需要注意的地方：

  1. 切分时，先将正文开头的标题部分提取出来，只对正文进行切分。
  2. 每个 Chunk 重新拼接标题前缀，确保文件标题也能参与后续的向量检索。

最终将切分后的 chunk_list 保存为本地文件 chunks.jsonl，供后续向量化和入库使用。

2.3 选择 Embedding 模型

不同 Embedding 模型在不同语言上的表现存在差异，因此需要根据实际资料选择合适的模型。

这里选择的是 BAAI/bge-m3。

选择它主要有以下几个原因：

  1. 中文检索效果较好。
  2. 支持最长 8192 Token 的输入。
  3. 同时支持稠密向量（Dense Vector）和稀疏向量（Sparse Vector）。
  4. 模型参数量约为 568M，可以在个人电脑的 8GB 显存显卡上运行。

最近在知乎看到有人讨论：为什么使用 Decoder 的 Embedding 层作为 RAG 的 Embedding 模型效果不好？这里简单解释一下。

Embedding 本质上是一种将输入映射为向量的模型结构，但模型最终具有什么能力，取决于它的训练目标。

举个例子，心脏是一种负责泵血的器官，小鼠和人类都有心脏，但这不意味着小鼠的心脏可以直接移植到人类身上。相同的模型结构，并不意味着具备相同的功能。

独立的 Embedding 模型通常会针对语义相似性进行训练，例如使用对比学习，将语义相近的文本向量拉近，将不相关的文本向量拉远。

而 Decoder 中的 Embedding 层通常跟随下一 Token 预测任务进行训练，其目标是为语言模型提供 Token 表示，而不是直接优化文本之间的语义相似度。

因此，不能因为 Decoder 中存在 Embedding 层，就直接将其拿来作为 RAG 的 Embedding 模型。

当然，也可以将预训练 Decoder 的 Embedding 层作为初始化参数，再通过对比学习等方式进行训练，使其具备适合 RAG 检索的能力。

实际上，Embedding 模型只需要完成一件事：将输入的 text_list 转换为向量并返回。

2.4 选择向量数据库

目前可供选择的向量数据库有很多，这里使用 Milvus Lite。

主要考虑以下两点：

  1. 功能：支持稠密向量和稀疏向量，也提供多种向量索引方式，可以满足本文的混合检索需求。
  2. 部署：Milvus Lite 可以通过 pip 安装，不需要单独部署 Docker 服务，适合目前的小规模数据。后续数据量增加时，也可以迁移到独立部署的 Milvus 服务。

初始化时，需要传入一个 Embedding 模型和一个 uri，用于指定数据库位置：

  • 传入本地路径时，使用 Milvus Lite。
  • 传入 Milvus 服务地址时，连接独立部署的 Milvus 服务。

对于本地数据库：

  1. 路径对应的数据库已存在时，打开已有数据库，保留其中的 Collection 和数据。
  2. 数据库不存在时，会创建一个新的空数据库，此时还没有任何 Collection，直接检索会报错。

在 create_collection() 中，需要定义 Collection 的 Schema，包括主键、稠密向量、正文和 Metadata 等字段。稠密向量的维度直接从 Embedding 模型的 dense_dim 属性中获取。

在 search() 中，采用的是 RRF（Reciprocal Rank Fusion）混合检索。

由于 BGE-M3 同时支持稠密向量和稀疏向量，因此可以分别进行两次检索：

  1. 稠密向量检索：根据向量之间的语义相似度查找相关内容。例如，搜索「远程桌面使用什么端口」，即使原文没有出现「远程桌面」这几个字，也可能检索到介绍 RDP 的内容。
  2. 稀疏向量检索：根据词语及其权重进行匹配。例如，搜索 3389，包含该数字的文本通常更容易获得较高的匹配得分。

两种检索方式各有侧重，组合起来可以同时利用语义信息和关键词信息。

RRF 则负责将两次检索得到的结果按照排名进行融合，而不是直接比较两种检索方式的原始得分。

需要注意的是，混合检索不一定始终优于单独使用稠密向量检索。具体效果还需要根据数据集和实际查询进行测试。

2.5 将数据、Embedding 模型和向量数据库组合成 RAG

前面的步骤分别完成了数据整理、文本切块、Embedding 模型和向量数据库的准备。

接下来，只需要将它们组合起来，就可以构建完整的 RAG 数据库。

这里通过一个统一的脚本编排整个流程。我们只需要提供原始数据所在的文件夹，以及 Embedding 模型等必要参数，就可以自动完成数据处理和向量入库。

最终会在 output 文件夹下生成以下文件：

  1. documents.jsonl：清洗、整理后的原始文档。
  2. documents_with_id.jsonl：添加了文档 ID 的原始文档。
  3. dict_id2document.json：文档 ID 与原始文档之间的映射关系。
  4. chunks.jsonl：切分后的文本块。
  5. port_service.db：Milvus Lite 数据库文件夹。

至此，RAG 数据库的构建流程就完成了。后续只需要加载对应的数据库和 Collection，就可以通过统一的检索接口查询相关资料。

3. RAG 放入MCP服务器中当工具

这里继续使用第一篇中开发的 cc_agent 框架，将 RAG 检索功能封装成 MCP 工具，供 Agent 按需调用。

首先，将准备好的资料数据放在 \cc_agent\mcp_server\data\nmap_notes 目录下，将 RAG 检索所依赖的代码放在 \cc_agent\mcp_server\dependences\rag_tools 目录下。

从目录结构可以看到，实际运行检索功能只需要两个数据文件：

  • db 文件夹：存放 Milvus 向量数据库。
  • dict_id2document.json：存放文档 ID 与原始文档内容的映射关系。

至于 rag_tools 中的代码，我直接将之前生成 RAG 知识库时使用的代码整体搬了过来。其中的数据收集、文本分块等模块在当前检索场景下并不需要，严格来说可以删除，但为了省事就暂时保留了。

接下来，在 \cc_agent\mcp_server\function 目录下创建 rag_search.py，实现 RAG 检索工具。

RAG_search(collection: CollectionType, query: str, top_k: int = 5) 中，Agent 只需提供资料集合 collection 和查询内容 query，top_k 通常使用默认值即可。

通过 build_description()，我们将可用的 collection 及其对应的资料说明动态写入工具描述，让 Agent 根据问题选择合适的资料集合，实现一级路由

 

 

4. 网络搜索

网络搜索工具的实现比较简单，可以直接整合现有的 API 服务：Tavily。

Tavily 是专门面向 AI Agent 的网络搜索服务，注册账号后可以获得一定的免费搜索额度。

我们在 \cc_agent\mcp_server\function 目录下创建 web_tools.py，实现两个工具：web_search 和 fetch_url。

web_tools.py 中包含两个工具：

  • web_search：调用 Tavily API 进行网络搜索，返回搜索结果的标题、来源网址和内容摘要。
  • fetch_url：根据指定 URL 提取网页正文，支持分段读取，并缓存已经获取的网页内容，避免重复请求。

从 web_search 的工具描述可以看到，它适用于内部资料库中没有的信息，以及需要获取最新信息的场景。如果搜索结果中的摘要不足以回答问题，Agent 可以进一步调用 fetch_url 获取网页正文。
