从零开始的LLM 10. mem0原理及API使用

发表于 2026-08-13 更新于 2026-08-16

前言

本文将介绍 mem0 的原理以及简单的agent制作。

经过前面的学习，我们已经系统地完成了大语言模型（LLM）的基础部分，主要参考了以下资料：

  • 《动手学深度学习》
  • 《蘑菇书》
  • 《Happy-LLM》
  • 《Hello-Agents》
  • 《all-in-rag》

到这里，可以认为已经具备了继续深入学习 Agent 的基础能力。

接下来的内容将不再像之前那样按照固定课程循序渐进，而是更多围绕当前 Agent 领域的研究方向展开。学习内容既会涉及工程实践（如各种 Agent 框架、工作流、记忆系统等），也会涉及算法与模型层面的探索（如多模态、持续学习等）。

  1. Generative Agents
  2. Letta
  3. A-MEM
  4. Voyager

这条路线主要围绕 Agent 的持续学习（Continual Learning） 展开，也是我目前最感兴趣的方向：如何让一个 Agent 在长期运行过程中不断积累经验、提升能力，而不是每次都从零开始。

目前来看，大致有两种思路：

  1. 不修改模型本身。 仅通过 Prompt、记忆系统（Memory）、RAG、工具调用等机制，使 Agent 能够不断积累知识和经验，实现能力的持续增长。
  2. 修改模型本身。 基于 Agent 长期运行过程中积累的对话、笔记和总结等数据，在合适的时机对模型进行持续训练（Continual Fine-tuning），使模型真正将这些经验内化，而不仅仅依赖外部记忆。

由于这一阶段更多是阅读论文、分析开源项目、验证实验以及整理个人理解，而不是单纯跟着教程学习，因此资料收集、实验和整理都会比之前花费更多时间。

相比之前学习的 A-MEM，mem0 在实际应用中的知名度和社区活跃度都更高，整体也更加成熟。本章节会花一些时间先了解 mem0 的核心原理，然后再基于 mem0 实现一个简单的 Agent。不过mem0的v2和v3 pipeline版本实现有非常大的不同，我们先讲论文中v2的实现，再分析v3的不同。

和之前的 A-MEM 类似，这次我们同样会把重点放在“记忆系统是如何融入 Agent”这件事情上。不过这次不再使用 LangGraph，整体实现会更加简单，也更方便我们直接理解 mem0 的使用方式。

1. Mem0 原理

论文地址：https://arxiv.org/abs/2504.19413

Mem0 的核心目标是：从对话中提取长期有价值的信息，并将这些信息持续写入、更新到长期记忆中，同时支持后续检索。

从整体流程来看，可以将 Mem0 理解为三个主要部分：

  1. Extraction：从对话中提取 candidate memories
  2. Update：将 candidate memories 与已有 memories 进行比较并更新
  3. Retrieval：从长期记忆中检索与当前 query 相关的信息

1.1 提取阶段（Extraction Phase）

Mem0 的记忆提取通常以一对消息作为当前输入，即：

  • 一条 user message
  • 一条 assistant response

可以表示为：

\[ (m_{t-1},m_t) \]

其中，\(m_t\) 表示当前消息，\(m_{t-1}\) 表示紧邻当前消息的上一条消息。

但是，仅仅将当前消息对交给 LLM 并不足以判断哪些信息值得长期保存。

因此，Mem0 会进一步提供一些历史上下文信息，共同构成 extraction 的输入。

1.1.1 当前消息对（Current Message Pair）

当前消息对：

1.1.2 对话总结（Conversation Summary / Summary Context）

如果每次提取记忆时，都把整个 conversation history 放进 LLM prompt，那么随着对话不断增长，prompt 会越来越长。

因此，Mem0 会维护一种对历史对话的压缩表示，用于在不保留全部原始消息的情况下，为 LLM 提供更长期的上下文。

Summary 解决的是“历史太长，无法全部放入 extraction prompt”的问题。

需要注意的是，S 是针对当前 conversation history 生成的总结信息，其作用是压缩当前 conversation 中的历史内容。因此，当开始一个新的 conversation 时，通常会对应新的 conversation context / summary，而不会直接继承上一段 conversation 的 S。

换句话说，S 主要用于帮助 extraction 阶段理解当前 conversation 的历史背景，而不是一个跨 conversation 永久保存的长期 memory。

1.1.3 最近的历史消息（Recent Messages）

除了 summary 之外，Mem0 还可以提供最近的一部分历史消息：

\[ {m_{t-n},m_{t-n+1},...,m_{t-2}} \]

这些消息用于保留比 summary 更具体、更细粒度的近期上下文。

这些信息可以帮助 LLM 判断当前消息中的内容是否与最近的对话有关。

1.1.4 Extraction Prompt

最终，Mem0 会将这些上下文共同提供给 LLM：

\[ P= \left( S, {m_{t-n},...,m_{t-2}}, (m_{t-1},m_t) \right) \]

其中：

  • \(S\)：历史 conversation 的 summary/context
  • \({m_{t-n},...,m_{t-2}}\)：最近的一部分历史消息
  • \((m_{t-1},m_t)\)：当前消息对

然后通过 LLM：

\[ \phi(P)\rightarrow\Omega \]

提取出一组值得考虑保存的候选记忆： \[ \Omega={\omega_1,\omega_2,...,\omega_n} \] 这些 \(\omega_i\) 可以称为：

candidate facts / candidate memories

Extraction 的任务是“发现可能值得保存的记忆”，而不是直接决定数据库最终应该保存什么。

最终是否 ADD、UPDATE、DELETE 或 NOOP，要在下一阶段决定。

1.2 更新阶段（Update Phase）

Extraction 得到： \[ \Omega={\omega_1,\omega_2,...,\omega_n} \] 之后，Mem0 需要判断：

这些新的 candidate memories 与数据库中已有的 memories 是什么关系？

因为不能简单地把每一次对话产生的新信息全部 ADD 到数据库。

否则：

最终数据库可能出现大量语义重复的 memory。

因此，对于每一个 candidate fact，Mem0 会首先从已有 memory 中检索语义上最相关的 memories（向量相似检索）。

可以抽象为：

对于每一个 candidate fact，Mem0 会将其与检索到的相关 existing memories 一起交给 LLM，由 LLM 判断应该对长期记忆执行哪一种操作：

操作 含义
ADD 数据库中不存在语义等价的 memory，因此创建新的 memory
UPDATE 已存在相关 memory，但新的信息可以对其进行补充或完善，因此更新已有 memory
DELETE 新信息与已有 memory 发生冲突，使原 memory 失效，因此删除或标记其为无效
NOOP 新信息不会对现有 knowledge base 产生实际变化，因此不做任何修改

1.3 Mem0 Graph Memory

前面的 Extraction + Update 主要解决的是：

从对话中提取长期记忆，并判断这些记忆应该如何写入或修改。

在此基础上，Mem0 还提供 Graph Memory，用于将记忆中的实体（Entity）及其关系（Relationship）结构化组织起来。

1.3.1 Graph 的基本结构

Mem0 的 Graph Memory 可以抽象表示为： \[ G=(V,E,L) \] 其中：

  • \(V\)：Nodes，表示实体（Entities）
  • \(E\)：Edges，表示实体之间的关系（Relationships）
  • \(L\)：Labels，表示实体的语义类型等标签信息

1.3.2 Node（实体节点）

Node 对应 Graph 中的一个 Entity，例如：Bob、Python、LangGraph、Google

每个 Node 主要包含：

  1. Entity Type：实体类型，例如 Bob → Person、Google → Organization
  2. Embedding Vector：实体的向量表示，用于语义匹配和检索
  3. Metadata：实体的其他元数据，例如创建时间等

1.3.3 Relationship（关系）

在 Graph 中，Relationship 对应连接两个 Node 的 Edge，用于表示两个 Entity 之间存在的语义关系。

一个 Relationship 可以表示为： \[ (v_s,r,v_d) \] 其中：

  • \(v_s\)：source node，即关系的起点
  • \(r\)：relationship，即两个实体之间的关系
  • \(v_d\)：destination node，即关系的终点

例如： \[ (Bob,\ learns,\ LangGraph) \] 其中：

  • Bob 是 source entity

2. mem0 v3 pipeline 版本变动

目前通过 pip install mem0ai 安装的最新 mem0 版本，其默认 Pipeline 已经采用 v3；而 mem0 论文中介绍的 Pipeline 主要对应 v2。

v3 相比 v2 在记忆写入、图数据组织以及检索方式等方面都进行了较大调整。因此，本节单独介绍 v2 → v3 的主要变化。

其中最显著的变化是：v3 不再使用 Neo4j 等外部图数据库，而是直接移除了原有的 Graph Memory，并将部分图结构能力合并到 Memory Store 中。

2.1 整体架构：从 Memory + Graph 转向 Memory-centric

v2 的整体架构可以理解为两部分：Memory Store + Graph Memory

其中：

  • Memory Store：负责存储和检索 memory；
  • Graph Memory：负责提取 Entity，并通过 Entity-to-Entity 的关系构建 Knowledge Graph。

v3 则移除了独立的 Graph Memory，直接用同一个数据库存储memory和entity：

也就是说，v3 不再维护一个独立的 Entity-to-Entity Knowledge Graph，而是将 Entity 作为 Memory 的检索辅助结构。

同时，原有图数据库相关代码被大幅移除，包括 mem0/graphs/、graph_memory.py 等，Neo4j、Memgraph、Kuzu、Apache AGE、Neptune 等外部图数据库也不再属于 OSS SDK 的 Graph Memory 实现。

这是 v3 在 Memory 层面最重要的变化之一。

  • 新旧 memory 不再通过覆盖的方式更新，而是通过 linked_memory_ids 建立关联；
  • 摘要 S、recent messages 和当前 message pair 等输入信息的整体构造逻辑没有发生根本变化，主要变化集中在提取之后的 Memory 处理阶段。

因此，v3 的核心思想可以概括为：

不主动覆盖旧 memory，而是持续增加新的 memory，并通过关联关系表达新旧信息之间的联系。

这样做的好处是避免错误覆盖历史信息。例如，“喜欢 Python” → “喜欢 Rust”并不一定意味着前者是错误的，也可能只是用户偏好随时间发生了变化。

因此，v3 更倾向于保留完整历史信息，以支持时间维度上的推理。

其代价也很明显：Memory 不再通过 UPDATE / DELETE 自动控制规模，因此会持续累积，需要额外的删除和管理机制。

手动删除机制

v3 仍然提供显式的 Memory 管理能力，例如：

  • delete(memory_id)：删除指定 memory；
  • delete_all(filters)：根据条件批量删除；
  • delete_linked=True：删除某条 memory 时，同时沿 linked_memory_ids 关联链删除相关的旧 memory，避免被替代的旧 memory 在后续检索中重新出现。

2.5 检索：Hybrid Search + Entity-aware Ranking

v3 的检索不再依赖 v2 的 Graph Retrieval，而是将多种检索方式进行融合，主要包括：

  1. 稠密检索（向量/语义）：将 query 转换为 embedding，与 Memory Store 中已有 memory 的 embedding 进行相似度匹配，找到语义上最相关的 memory。
  2. 稀疏检索（关键词）：利用 query 中的关键词、实体等信息，对 memory 文本进行关键词匹配，弥补纯向量检索可能遗漏的结果。
  3. Entity-aware Ranking：从 query 中提取关键 entity，并利用已经建立的 Entity → Memory 关联，找到与这些 entity 相关的 memory。

最终综合 semantic similarity、entity information 以及 metadata 等信息 对候选 memory 进行排序，选择排名靠前的结果。

2.6 v2 → v3 的核心变化总结

v2 → v3 的核心变化主要有以下四点：

  1. Memory 写入：从 ADD / UPDATE / DELETE / NOOP 转变为以 ADD 为主的累积式记忆，通过 linked_memory_ids 关联新旧 memory。
  2. Graph Memory：移除 Neo4j 等外部图数据库，不再维护 Entity → Entity 的 Knowledge Graph，改为 Entity → Memory 的关联机制。
  3. Entity 提取：从原来的 Graph Memory 机制转变为使用 spaCy（非 LLM） 提取 Entity，并建立 Entity Index。
  4. Memory 检索：从原来的 Graph Retrieval 转变为 Hybrid Search + Entity-aware Ranking。

总体来说，v3 的设计目标是：

简化架构、降低延迟、减少旧记忆被错误覆盖的风险，同时保留 Entity 对 Memory 检索的辅助能力。
