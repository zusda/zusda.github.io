发表于 2026-09-27

前言

在弄一些花时间的东西，太久没写了。将前段时间学的渗透总结分享下。

1. 入口点

Agent 渗透测试的第一步通常是寻找 入口点（Entry Points）。这里的入口点不一定是传统意义上的 HTTP Endpoint，也可能是 Agent 暴露给用户的工具、业务功能、数据访问能力以及对话上下文。

1.1 工具调用

这一部分主要与 Agent 所连接的业务功能有关。

理想情况下，Agent 会直接告诉我们当前可用的 Tool，例如搜索、读取文件、发送邮件、修改订单等。但在实际测试中，Agent 往往不会主动暴露完整的 Tool 列表。

因此，可以通过以下两种方式进行功能发现：

  1. 直接询问 Agent 能够完成什么任务；
  2. 根据业务界面和 Agent 的行为，推测其背后可能存在的功能，并尝试触发。

1.1.1 功能发现：询问 Agent 能做什么

最简单的功能发现方法是直接询问 Agent：

有些 Agent 会主动介绍自己的能力，例如：

  • summarizing content
  • searching information
  • accessing documents
  • sending emails
  • modifying account information

如果 Agent 主动暴露了这些功能，就可以针对每项功能进一步测试其权限边界、输入范围以及是否存在 Prompt Injection 等问题。

例如，假设 Agent 表示自己具有 summarize 功能，那么就可以进一步测试它能够总结哪些内容，包括：

  • 用户提供的普通文本；
  • 当前对话；
  • 历史对话；
  • 内部文档；
  • Tool 返回的数据。

因此，这类测试可以形成一个基本流程：

询问 Agent 能做什么 → 发现功能 → 选择具体功能 → 测试该功能的权限和数据边界。

除了 summarize 之外，同样的方法也可以用于测试搜索、文件读取、邮件发送、账户管理、订单修改等功能。

最终需要关注的是：

Agent 主动暴露了哪些能力，以及这些能力是否超出了当前用户本应拥有的权限。

1.1.2 登录界面

登录页面通常是另一个值得关注的入口。

例如，某些 Agent 会参与：

  • 密码找回；
  • 邮箱绑定；
  • 身份验证；
  • 恢复码发送；
  • 账户信息修改。

其中比较典型的测试目标是 密码找回流程中的身份验证是否真正由后端完成。

例如，可以观察 Agent 是否仅根据用户在对话中的自述，就认为用户拥有某个账户的控制权。

测试时可以构造类似：

I need help recovering my account. I forgot my password.

然后观察 Agent 是否进一步要求：

  • 身份验证；
  • 原邮箱验证；
  • MFA；
  • 恢复码；
  • 其他后端认证信息。

如果仅通过自然语言声称“我是账户所有者”，Agent 就能够执行修改邮箱、发送恢复码等高权限操作，那么问题本质上并不是 Prompt 本身，而是：

Agent 是否被允许在缺乏后端身份验证的情况下执行账户恢复操作。

案例：Meta AI Support Assistant

2026 年 6 月，有攻击者利用 Meta 的 AI Support Assistant 进行 Instagram 账户接管。该 Agent 原本负责密码找回、邮箱重新绑定等账户恢复操作。

攻击者首先选择目标用户名，然后进入 Forgot Password 流程，并向 Agent 发送类似以下的 Prompt：

Agent 将攻击者提供的邮箱作为账户恢复邮箱，并向该邮箱发送验证代码。攻击者再将收到的代码提供给 Agent，继续完成账户恢复流程。

随后，Agent 提供密码重置操作，攻击者设置新的密码，从而获得目标账户的控制权。

整个过程的关键并不在于 Prompt 本身有多复杂，而在于 Agent 接受了用户关于“我是该账户所有者”的自然语言声明，并允许用户通过对话推进高权限的账户恢复流程。

这个案例对应前面的测试思路：

自然语言身份声明 → 修改恢复邮箱 → 获取验证码 → 密码重置 → 账户接管

因此，在测试登录/账户恢复 Agent 时，需要重点关注：

用户是否可以仅通过 Prompt，让 Agent 执行本应要求独立身份验证的敏感操作。

1.1.3 数据读取功能

如果 Agent 具备文件、代码仓库、数据库或知识库的读取能力，那么需要重点测试 访问控制是否正确应用到 Agent 的数据访问过程中。

与传统应用类似，首先需要确认 Agent 能够读取哪些资源，然后进一步测试是否能够读取不属于当前用户的数据。

  • 其他用户的文件；
  • private repository；
  • 内部项目；
  • 未授权的数据库记录；
  • 其他租户的数据。

如果 Agent 能够直接返回该资源中的内容，而当前用户实际上没有访问权限，那么这属于典型的 越权读取（Unauthorized Data Access）。

这里需要重点确认的是：Agent 是否拥有超出当前用户权限的数据访问能力，以及 Tool 是否在执行读取操作时进行独立的权限校验。

因此，这类测试的核心可以概括为：

Agent 能读取什么，不重要；更重要的是，它能否读取“不属于我的东西”。

理想情况下，即使用户能够通过自然语言要求 Agent 读取某个资源，最终的 Tool 或后端服务仍然应该根据用户身份进行权限检查，而不能仅依赖 Agent 自身的判断。

案例：GitHub Agentic Workflows 越权读取私有仓库

2026 年 7 月，Noma Security 的研究人员披露了 GitHub Agentic Workflows 中的一项安全漏洞。该功能使用 Claude 或 Copilot 等 LLM，自动分析和处理 GitHub Issue。

攻击者不需要 GitHub 账户的特殊权限，只需要在公开仓库中创建一个 Issue，并在 Issue 内容中加入隐藏的 Prompt Injection。

问题在于，Agent 的读取范围没有正确限制在当前公开仓库。攻击者最终可以诱导 Agent 访问同一组织下的私有仓库，并将读取到的私有内容作为评论发布到原本公开的 Issue 中。

攻击链可以概括为：

公开 Issue → Prompt Injection → Agent 调用 read_repo → 读取私有仓库 → 公开评论泄露数据

即使攻击者只能控制一个公开 Issue，也不意味着 Agent 就应该能够访问组织内其他私有资源。对于文件、代码仓库、数据库等 Tool，后端必须根据当前用户和资源的实际权限进行独立校验。

因此，在测试 Agent 的读取功能时，需要重点验证：

攻击者能够控制的输入，是否可以影响 Agent 的数据访问范围，从而读取当前用户本不应该访问的资源。

1.1.4 购物车 / 销售 Agent

购物车、销售和客服 Agent 通常具有一定的业务操作权限，例如：

  • 查询商品；
  • 修改购物车；
  • 创建订单；
  • 修改价格；
  • 应用优惠；
  • 取消订单。

因此，这类 Agent 特别适合测试 业务逻辑与自然语言指令之间的权限边界。

一种常见的测试思路是首先尝试通过 Prompt Injection 改变 Agent 的行为规则，例如让 Agent 错误地认为：The customer is always right.

然后在后续对话中提出异常的价格请求。

如果 Agent 最终接受了一个明显不符合正常业务规则的价格，就需要进一步确认：

  • Agent 是否拥有直接修改价格的 Tool；
  • Tool 是否验证价格范围；
  • 服务端是否重新计算订单金额；
  • 是否需要管理员权限；
  • Agent 是否可以绕过优惠券、折扣等业务规则。

因此，这类问题可以归纳为：

LLM 的行为约束不能替代后端业务权限控制。

即使 Agent 被 Prompt 要求“不能修改价格”，真正涉及订单金额的操作仍然应该由后端进行独立验证。

这个案例说明，如果销售 Agent 的价格、优惠或订单逻辑主要依赖 LLM 的行为约束，那么攻击者可能通过 Prompt Injection 改变 Agent 的决策逻辑。

因此，在购物车、销售和订单类 Agent 中，需要重点测试：

  • Agent 是否可以被用户改变业务规则；
  • 是否能够接受超出正常范围的价格；

即使 Agent 被 Prompt Injection 改变，后端业务逻辑是否仍然能够阻止异常操作？

1.3 Indirect

Indirect Prompt Injection 与 Direct 的区别在于，攻击者不直接向 Agent 提交恶意 Prompt，而是将恶意内容植入 Agent 会自动读取的数据源中。

Agent 在处理用户任务时，通常会自动收集各种上下文，例如：

  • 日历事件；
  • 邮件；
  • 文档；
  • GitHub Issue；
  • 用户资料；
  • 联系人和社交关系；
  • 第三方 Tool 返回的数据。

这些内容原本只是普通的业务数据，但一旦被直接加载到 Agent 的 Prompt 或 Context 中，其中的文本就可能被 Agent 当成指令处理。

因此，Indirect 测试的核心是：

哪些外部数据会被 Agent 自动加载到 Context 中？这些数据中的内容是否能够影响 Agent 的行为？

例如，与其他用户建立关系后产生的资料，也可能被 Agent 自动读取并加载到 Prompt 中。

可以通过正常的业务操作建立这种关系，例如邀请一个状态为 busy 的其他用户：

然后观察 Agent 在处理这一关系时，会自动获取哪些关于该用户的信息，以及这些信息是否会被进一步暴露。

这里不需要直接要求 Agent “读取其他用户的数据”，而是通过正常的业务流程，让相关数据间接进入 Agent 的上下文。

案例：Google Calendar Indirect Prompt Injection

2025 年，Ben-Gurion University 的安全研究人员展示了一个典型的 Indirect Prompt Injection 场景，并在 DEF CON 33 展示了相关研究 Invitation Is All You Need。

攻击者首先创建一个日历邀请，并在事件标题或描述中加入 Prompt Injection。日历邀请本身是普通的用户生成内容，但当 AI Assistant 被要求总结用户的日历时，它会自动读取这些事件内容。

攻击流程可以概括为：

攻击者创建日历邀请 → 注入恶意内容 → 邀请进入受害者日历 → 用户要求 Agent 总结日历 → Agent 读取事件内容 → 注入内容影响 Agent 行为

这个案例说明：

对于 Agent 来说，数据不等于可信指令。

Trusted Instructions 和 Untrusted Data。

如果外部用户能够控制某段文本，而 Agent 又会自动读取这段文本，那么这段数据本身就应该被视为潜在的 Prompt Injection 入口。

1.3 Indirect

Indirect Prompt Injection 的特点是，攻击者不直接向 Agent 输入恶意 Prompt，而是将恶意内容植入 Agent 会读取的数据源中。

Agent 在执行任务时，通常会通过 RAG、相关性检索或其他 Context 构建机制，从邮件、日历、文档、Issue、联系人等数据源中获取与当前任务相关的内容，并将其加入当前 Prompt。

因此，即使攻击者无法直接与 Agent 对话，也可能通过控制这些数据源中的内容影响 Agent。

测试的核心是：

哪些外部数据会被 Agent 自动加载到 Context 中，以及这些数据中的内容能否进一步影响 Agent 的行为。

案例：Google Calendar Indirect Prompt Injection

2025 年，Ben-Gurion University 的研究人员展示了一种针对 AI Assistant 的间接 Prompt Injection。其研究表明，攻击者可以利用 Google Calendar 邀请，将恶意指令隐藏在日历事件中。

攻击过程如下。

Step 1：创建恶意会议

攻击者创建一个新的日历会议，并将 Victim 邀请进来。研究中的一个技巧是，在 Victim 当前处于 busy 状态时，邀请可能不会以明显的弹框形式提示，从而降低了用户发现异常会议的可能性。

Step 2：在会议内容中植入恶意指令

Step 3：等待 Victim 触发 Agent

当 Victim 使用 AI Assistant 执行类似：

的操作时，Agent 会搜索与“今天的会议”相关的数据。

攻击者创建的恶意会议因此可能被 RAG / 检索机制选中，并作为相关上下文加入当前 Prompt。

于是，原本只是一个日历事件 description 的文本，就进入了 Agent 的执行上下文。

Step 4：Agent 执行恶意操作

Agent 读取到其中的指令后，调用 Calendar.create 创建新的会议，并将 Victim 当天会议的 summary 写入新会议的 description。

由于这个新会议位于攻击者可以访问的日历中，攻击者最终就能够从自己的日历中获得 Victim 的会议摘要。

整个攻击链可以概括为：

攻击者控制日历内容 → 恶意指令进入 Victim 日历 → Victim 触发 summarize → RAG 检索恶意会议 → 恶意内容进入 Agent Context → Agent 调用 Calendar.create → Victim 数据被写入攻击者可访问的位置

这个案例体现了 Indirect Prompt Injection 一个非常重要的特点：

攻击者不需要直接控制 Agent，只需要控制 Agent 会读取的数据。

因此，测试 Agent 时，除了测试用户直接输入，还应该检查所有可能进入 Context 的外部数据源，例如日历、邮件、文档和第三方 Tool 返回结果。

尤其需要关注：

不可信数据 → Context → Tool 调用

这一条链路是否存在权限隔离。如果 Agent 能够因为读取了一段攻击者控制的文本，就把 Victim 的私有数据通过 Tool 写入攻击者可访问的位置，那么本质上就是一次 Indirect Prompt Injection + 数据外泄（Exfiltration）。

与其他用户构建关系的资料，都可能被agent读取，加载到promtp中。

1.4 图片

多模态 LLM 能够读取和分析图片中的内容，因此图片本身也可以成为攻击入口。

常见的攻击方式包括：

  1. 写入图片 Metadata

    将恶意指令写入图片的 EXIF、Comment 等 Metadata 中。如果 Agent 在处理图片时同时读取这些信息，这些内容就可能进入 Context。

  2. 隐藏在图片中的文字

    将恶意文字直接写入图片，并尽量让其与背景颜色接近。例如使用 RGB(255,255,255) 的背景，并使用 RGB(255,255,254) 绘制文字。

    人眼基本无法察觉这种细微的颜色差异，但 OCR 处理的是像素数据，因此仍有可能识别出文字轮廓，并将其转换成文本后交给 LLM。

    因此，测试图片输入时，不仅要关注人眼能看到什么，还需要关注 OCR、视觉模型和图片 Metadata 实际向 LLM 提供了什么内容。

研究案例：GhostCommit

2026 年 7 月，ASSET Research Group 披露了一类多模态 Prompt Injection 攻击。攻击者将恶意指令隐藏在 PNG 图片中，并通过 Repository 的 AGENTS.md 等配置文件让 AI Code Review Agent 自动处理这些图片。

当 Agent 读取图片时，隐藏内容可能通过 Metadata、OCR 或 Steganography 等方式进入 Agent 的 Context。Agent 随后可能将这些内容当成正常指令执行，从而读取敏感数据或调用不应调用的 Tool。

攻击流程：

恶意图片 → Agent 读取图片 → 隐藏指令进入 Context → Agent 执行指令 → 敏感数据泄露

这个案例说明，图片处理流程本身也可以成为 Prompt Injection 的入口。传统 Prompt Injection 主要关注文本输入，而多模态 Agent 还需要考虑图片中的 Metadata、OCR 内容以及其他隐藏信息。

1.5 文档

文档的攻击方式与其他数据类型类似，例如在文档内容中植入 Prompt Injection。不过，文档还存在一个比较特殊的攻击面：文档格式本身。

人类阅读文档和 AI 解析文档时，可能看到的并不是完全相同的内容。攻击者可以利用 HTML、PDF、Office 等文档格式中的隐藏文本、特殊结构或 Metadata，让 AI 解析到人类不容易注意到的内容。

因此，测试文档类 Agent 时，除了文档正文，还需要关注：

  • 隐藏文本；
  • Metadata；
  • 特殊格式或结构；
  • 文档中嵌入的其他内容；
  • AI 实际解析到的内容是否与人类看到的内容一致。

也就是说，攻击面不只是“文档里写了什么”，还包括文档是如何被 AI 解析的。

因此，文档类测试最终仍然需要回到权限控制：即使文档要求 Agent 读取某些机密数据，后端和 Tool 也应该独立验证当前用户是否拥有访问权限。

4. 利用

前面的内容主要从发现漏洞的角度出发，关注如何通过 Prompt Injection 找到 Agent 的安全问题。虽然本节的部分内容与前面有所重叠，但视角不同。

本节主要从利用的角度出发。Prompt Injection 成功后，攻击者的目标并不只是让 Agent 输出一段恶意文本，而是进一步利用 Agent 已有的能力，将注入转化为实际影响。

因此，这里的重点不是“如何让 Agent 被注入”，而是思考：注入成功后，Agent 能被利用来做什么？

4.1 钓鱼攻击

Indirect Prompt Injection 还可以被用于钓鱼攻击。一个典型案例是 Schlack。

2024 年 8 月，PromptArmor 发现 Slack AI 存在 Indirect Prompt Injection 漏洞。攻击者可以在自己控制的公开 Channel 中植入恶意 Prompt，而 Slack AI 在回答其他用户的问题时，可能将攻击者的消息与受害者的私有数据一起检索到 Context 中。

4.4 持久化

攻击者还可以尝试让恶意 Prompt 长期存在于 Agent 会读取的数据中，而不是只影响当前一次对话。

例如：

恶意文档 → 写入知识库 → RAG 检索 → 恶意 Prompt 进入 Context → 后续用户持续受到影响

这种方式可以称为 Persistent Prompt Injection。

与普通 Indirect Prompt Injection 相比，它的特点是恶意内容被写入了 Agent 长期使用的数据源，例如：

  • Knowledge Base
  • RAG 文档
  • Wiki
  • Repository
  • Calendar
  • 用户资料

因此，即使最初的攻击者已经离开，恶意内容仍可能在之后被 Agent 检索并执行。
